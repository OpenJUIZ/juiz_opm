# 0007 juiz-OPL は 1 文 1 事実の英語の文にし、注釈は文末の括弧に書く

- 状態: 採用(案。文の言い回しは ISO 19450 の本文か Dov Dori 先生の返事で見直す)
- 日付: 2026-11-06

## 背景

[0002](0002-open-points.md) の 5 で英語の OPL を正本にし、[0005](0005-metamodel-layers.md) でモデルが持つものを表にし、[0006](0006-xml-format.md) で XML に写した。roadmap の Step 3 として、同じ表を文で書く文法、整形式の規則、正規形を決める。ISO 19450 の本文はこの環境から読めていない。

## 決めたこと

詳細は [spec/opl.md](../../spec/opl.md)。

1. **1 文 1 事実。** 文は Thing 1 つ、State の並び、リンク 1 本、InZoom 1 つ、Fan 1 つのどれかを書く。並びの文(`P requires A and B.`)は入力では受けるが、正規形では使わない。
2. **名前は大文字で始まる語なら引用せず、それ以外は `"` で引用する。** 骨組みの語は小文字なので、Thing の名前と予約語はぶつからない。juiz の名前(`talker0`)は引用すれば OPM の名前にそのまま使える。State の名前は小文字 1 語なら引用しない。
3. **Thing はどれも宣言の文を持つ。** `Camera is a physical object.` の形で kind・essence・affiliation を書き、id・description・注釈もここに書く。未宣言の名前は誤り。
4. **modifier は ISO 風の長い文で書く。** event は `A initiates P, which requires A.`、condition は `P occurs if A is s, otherwise P is skipped.`。self-invocation は `P invokes itself.`。
5. **juiz の注釈は文末の `[鍵: 値, ...]`、文の形を持たないコアの属性(id、description、duration、ordered)は `{...}` に書く。** 鍵はメタモデルの名前から `juiz:` を外したもの。`[...]` を取り除けばコアだけの OPL になる。
6. **図の層(OPD、配置)と juiz 以外の名前空間は OPL に書かない。** 図はモデルから描くもので、保ちたいときは XML を使う。
7. **id は既定では書かず、名前から決まった規則で作る。** id を保ちたいときは全要素に `{id: ...}` を書く形で書き出す。往復テストは、id を書く形では id まで、書かない形では id の付け替えを除いて一致を見る。
8. **正規形は Thing ごとのまとまりを名前の順に並べる。** まとまりの中は宣言、State、InZoom、リンク(kind の順、次に文の文字列の順)。リンクは Process の側(invocation と構造リンクは source)の Thing のまとまりに入る。

## 理由

- 1 文 1 事実にすると、モデルと文の間が一対一になり、往復テストで比べられる。
- 大文字で始まる名前と小文字の骨組みの語で分けると、引用なしで読める文が多く、解析は先読み 1〜2 語で決まる。
- 注釈を文の中の言い回しにすると語彙が増え、標準の OPL に戻す写像も複雑になる。末尾の括弧なら、取り除くだけで標準に近い文になる。
- Thing ごとにまとめると、Capture の書き込み・戻り値・起動のように、1 つの Process の事実が続けて読める。

## 影響

- Step 5 の opm_opl はこの文法を解析し、O1〜O11 を検査し、正規形で書き出す。id を書く形を選択肢にする。
- Step 7 で conf から作るときの OPM の名前の付け方を決める。
- ISO 19450 の OPL の形式文法を読めたら、言い回しを合わせる新しい決定を足し、今の形は入力の別名として残す。
